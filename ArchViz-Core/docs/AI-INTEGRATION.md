# AI 集成与提示工程指南

> 本文档深入解析 ArchViz-Core 中两大 AI 能力（动画生成 + 图像渲染）的架构设计与提示工程方法论。
> 相关架构背景参见 [整体架构文档](./ARCHITECTURE.md)。

## 1. AI 功能概述

ArchViz-Core 集成了两类 AI 能力，分别面向不同的设计工作流：

| 能力 | 用途 | AI 服务 | 交互方式 |
|------|------|---------|---------|
| **AI 动画生成** | 自然语言 → 24 秒建筑动画脚本 | 大语言模型（LLM） | 文本输入 → 自动执行 |
| **AI 图像渲染** | 视口截图 + 提示词 → 风格化效果图 | 图像生成模型（多渠道） | 截图 + 文本 → 图片输出 |

两者共享同一套 API 代理层架构（详见 [API 设计模式文档](./API-DESIGN-PATTERNS.md)），但在前端的调用模式截然不同。

## 2. AI 动画生成系统

### 2.1 双阶段架构的设计动机

早期版本采用单阶段设计：用户描述直接让 LLM 输出底层动作脚本。实践中发现以下问题：

- LLM 容易输出无效的相机坐标和不合理的时间分配
- 修复一个底层动作错误需要重新生成整个脚本
- 用户的高层意图（"从远景到近景"）被直接翻译为低层参数，缺乏中间抽象

因此引入 **双阶段架构**：

```
┌─────────────────────────────────────────────────────────────┐
│  Stage 1: AIAnimationPlanner（导演层）                        │
│                                                             │
│  用户自然语言 ──▶ LLM ──▶ 导演分镜规划（Shot Plan）            │
│  "展示建筑全貌，然后剖切"  →  [{goal, movement, focus}, ...]  │
└────────────────────────┬────────────────────────────────────┘
                         │  高层抽象（意图级）
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  Stage 2: AIAnimationExecutor（技术层）                       │
│                                                             │
│  分镜规划 ──▶ LLM / 规则引擎 ──▶ 可执行时间线（Timeline）     │
│  [{goal:"建立认知", movement:"orbit"}]                       │
│      →  [{action:"rotateObject", params:{from:0, to:360}}]  │
└─────────────────────────────────────────────────────────────┘
```

**核心收益**：

- **关注点分离**：导演只负责"拍什么"，技术层负责"怎么拍"
- **错误隔离**：分镜规划的格式简单，LLM 出错概率低；技术层可用规则引擎兜底
- **可调试性**：两阶段的中间产物（Shot Plan）可独立审查和修改

### 2.2 提示工程框架

#### 角色定义区

系统提示的开头为 LLM 赋予一个专业身份：

```
"你是一个专业的3D建筑可视化动画导演。"
```

**设计考量**：给定明确角色可以将 LLM 的回答锚定在建筑可视化领域，减少无关联想。实验发现，带角色的提示比通用提示在格式遵从度上高约 30%。

#### 能力约束区

紧接角色定义，提供一份**穷举的能力清单**：

```
可用能力清单：
1. 相机控制：正交/透视/两点透视切换、位置移动、目标点设置
2. 模型变换：绕Y轴旋转、缩放
3. 分析功能：剖切(x/y/z轴)、边界框、参考小人
4. 光照与效果：太阳角度、预设风格、后期特效
5. 通用参数：自动旋转、光照循环、网格显示
```

**设计考量**：LLM 天然倾向于"发挥创造力"，可能输出系统根本不支持的动作（如"相机抖动效果"）。通过显式列出所有可用动作，将 LLM 的输出空间约束到引擎实际支持的能力范围内。

#### 输出格式区

严格定义 JSON 结构化输出格式，并附带一个完整示例：

```
输出要求：必须严格使用以下JSON格式，只返回JSON，不包含其他内容：
{
  "version": "1.1",
  "metadata": {"title": "描述", "duration": 24, "fps": 30},
  "timeline": [{ "time": 0, "duration": 5, "action": "...", "params": {} }]
}
```

**设计考量**：

- "只返回 JSON" 避免 LLM 输出解释性文字，降低解析难度
- 固定 `duration: 24` 消除了时长协商的歧义
- 提供完整示例比仅提供 schema 更有效——LLM 是模式匹配器，示例是最好的约束

#### 上下文注入

在技术层的提示中注入当前场景状态：

```
当前场景信息：
- 模型尺寸：{modelSize}m
- 模型包围盒：{bounds}
- 当前相机模式：{cameraMode}
- 当前风格：{currentPreset}
```

这使 LLM 生成的坐标和参数能够适配实际模型的尺度。

### 2.3 动画脚本的校验与修复

LLM 输出不可信，必须经过严格的后处理管线：

```
LLM 原始输出
    │
    ▼
[1] JSON 提取 ── 处理 Markdown 围栏、尾逗号、注释
    │
    ▼
[2] 结构校验 ── version/metadata/timeline 字段存在性
    │
    ▼
[3] 动作校验 ── action 是否在允许列表内
    │
    ▼
[4] 时间线修复 ── 动作数量裁剪（≤48个）
    │              最短持续时间保障（≥0.05秒）
    │              时间重叠检测与修正
    │
    ▼
[5] 参数修复 ── 枚举值拼写纠正
    │             数值范围钳制
    │             缺失参数填充默认值
    │
    ▼
合法的动画脚本
```

设计了 **重试预算** 机制：导演层允许 1 次重试，技术层允许 2 次重试。重试时会将上一次的错误信息注入到修复提示中，引导 LLM 纠正具体问题。

### 2.4 从自然语言到动画序列的转换流程

```
"先缓慢旋转一圈，然后从上往下剖切展示内部结构"
    │
    ▼ [Stage 1: Planner]
    │
Shot Plan:
  Shot 1: {goal:"建立整体认知", movement:"orbit", duration:12}
  Shot 2: {goal:"展示内部结构", movement:"sectionReveal", axis:"y", duration:12}
    │
    ▼ [Stage 2: Executor]
    │
Timeline:
  [0s-12s]  rotateObject  {axis:"y", from:0, to:360, easing:"easeInOutSine"}
  [12s-14s] applyPreset   {name:"Ghosted"}
  [14s-24s] sectionCut    {axis:"y", from:50, to:-30, easing:"easeInOutCubic"}
```

## 3. AI 图像渲染系统

### 3.1 多渠道设计

系统支持三个 AI 图像渲染服务：

```
┌───────────────┐     ┌───────────────┐     ┌───────────────┐
│    阿里云      │     │    FLUX       │     │  火山引擎      │
│  (DashScope)  │     │ (BFL Labs)    │     │  (即梦 4.0)    │
└───────┬───────┘     └───────┬───────┘     └───────┬───────┘
        │                     │                     │
        └─────────┬───────────┴─────────────────────┘
                  │
           ┌──────▼──────┐
           │  统一渠道接口 │
           │  (provider)  │
           └──────────────┘
```

**为什么不锁定单一服务商**：

- **可用性**：单个服务的 API 可能临时不可用
- **成本控制**：不同服务在不同场景下的性价比不同
- **质量多样性**：不同模型在建筑风格渲染上各有优势
- **供应商风险**：避免被单一服务商绑定

### 3.2 抽象工厂模式的应用

前端通过统一的 `provider` 参数选择渠道，代理层根据 provider 分发到对应的处理函数：

```javascript
// 伪代码：渠道分发
switch (provider) {
    case 'aliyun':
        result = renderWithAliyun(prompt, imageBase64);
        break;
    case 'flux':
        result = renderWithFlux(prompt, imageBase64, testKey);
        break;
    case 'volcano':
        result = renderWithVolcano(prompt, imageBase64);
        break;
}
```

每个渠道处理函数内部遵循相同的三步模式：**创建任务 → 轮询状态 → 提取结果**。尽管不同服务的请求格式和认证方式各异，但对前端暴露的接口始终是 `{image_url: string}`。

### 3.3 异步任务管理

AI 图像生成通常耗时 15-60 秒，不可能同步等待。系统采用 **后端轮询** 模式：

```
前端 ────── POST /api/render ──────▶ 后端代理
                                        │
                                        ├── 创建任务 → 获取 taskId
                                        │
                                        ├── 循环 {
                                        │     sleep(2s)
                                        │     GET /tasks/{taskId}
                                        │     if (完成) break
                                        │     if (失败) 抛出异常
                                        │   }
                                        │
前端 ◀── {image_url} ──────────────── 返回结果
```

**为什么选择后端轮询而非前端轮询**：

- 避免暴露第三方 API 的 taskId 和查询端点
- 后端可以处理不同服务的轮询协议差异
- 简化前端逻辑——一个 POST 请求得到最终结果

### 3.4 图生图管线

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 视口截图  │ ──▶│ Base64   │ ──▶│ 风格提示  │ ──▶│ AI 渲染   │
│ (WebGL)  │    │ 编码     │    │ 词组合   │    │ (云端)    │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
                                                     │
                                              ┌──────▼──────┐
                                              │  结果预览    │
                                              │  下载/分享   │
                                              └─────────────┘
```

截图通过 `renderer.domElement.toDataURL()` 获取，利用了 WebGL 渲染器的 `preserveDrawingBuffer: true` 配置。

## 4. API 代理层设计

### 4.1 为什么需要后端代理

三个不可妥协的理由：

1. **CORS 限制**：浏览器禁止前端直接请求不同源的 API
2. **密钥保护**：API 密钥不能出现在前端代码中
3. **请求格式转换**：不同 AI 服务的请求/响应格式差异大，代理层负责统一化

### 4.2 代理层的职责链

```
前端请求 ──▶ [路由分发] ──▶ [参数校验] ──▶ [密钥注入]
                                              │
                                              ▼
                                        [请求转发] ──▶ 第三方 API
                                              │
                                              ▼
                                        [响应标准化] ──▶ 前端
                                              │
                                              ▼
                                        [错误处理] ──▶ 统一错误格式
```

详细的代理层设计模式请参阅 [API 设计模式文档](./API-DESIGN-PATTERNS.md)。

## 5. 批量配置系统

### 5.1 预设视角配置的设计思路

建筑表现图有标准化的出图需求（轴测图、立面图、透视图、剖面图等），系统预定义了 6 类、共计数十个相机配置：

| 配置类型 | 数量 | 关键参数 |
|---------|------|---------|
| axonometric（轴测） | 8 | 正交相机、4方位 × 2仰角 |
| elevation（正交立面） | 6 | 正交相机、6个标准视图方向 |
| perspective（透视） | 8 | 透视相机、4方位 × 2仰角 |
| section（剖切） | 15 | 3轴 × 5偏移量 |
| twoPointPerspective | 5 | 两点透视、5方位 |
| stylePresets（风格） | 10 | 10种视觉风格遍历 |

### 5.2 配置数据结构

每个预设包含足以完全确定一张出图状态的参数：

```javascript
// 伪代码：单个预设配置的结构
{
    name: '西北轴测',           // 人类可读名称
    rotation: 0,               // 模型绕Y轴旋转角度（弧度）
    cameraMode: 'ortho',       // 相机模式
    viewAngle: [45, 30, 0],    // 方位角/仰角/滚转角
    fov: 45,                   // 透视模式下的视场角
    section: {                 // 可选的剖切参数
        active: true,
        axis: 'y',
        offset: 25
    },
    style: 'Clay'              // 可选的风格预设名
}
```

批量导出时，系统遍历所有配置，依次设置相机/剖切/风格状态，截取截图，最终打包为 ZIP 文件。
