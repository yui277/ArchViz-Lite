# 渲染管线技术文档

> 本文档深入解析 ArchViz-Core 的 Three.js 渲染管线设计，涵盖双相机系统、光照模型、后期处理、剖切渲染和自定义着色器。
> 架构概览参见 [整体架构文档](./ARCHITECTURE.md)。

## 1. Three.js 渲染管线基础

### 1.1 标准渲染流程

```
场景图(Scene Graph)                 相机(Camera)
    │                                   │
    ├── 灯光                            │
    ├── 模型网格                         │
    ├── 辅助几何体                       │
    └── 后期处理组合器                    │
         │                              │
         ▼                              ▼
    ┌─────────────────────────────────────┐
    │        WebGL 渲染器                  │
    │  (WebGLRenderer)                    │
    │                                     │
    │  顶点着色器 → 光栅化 → 片段着色器    │
    │        → 深度测试 → 模板测试         │
    │            → 混合 → 帧缓冲          │
    └─────────────────┬───────────────────┘
                      │
                      ▼
                ┌───────────┐
                │   屏幕     │
                └───────────┘
```

### 1.2 WebGL 渲染上下文的关键配置

ArchViz-Core 的渲染器初始化选择了几个对建筑可视化至关重要的选项：

| 选项 | 值 | 设计理由 |
|------|-----|---------|
| `antialias` | `true` | 建筑模型的直线边缘对锯齿极其敏感，MSAA 是性价比最高的方案 |
| `alpha` | `true` | 支持透明背景导出，便于后期合成 |
| `preserveDrawingBuffer` | `true` | 必须保留帧缓冲内容才能执行 `toDataURL()` 截图 |
| `logarithmicDepthBuffer` | `true` | 建筑模型尺度跨度大（室内家具 vs 城市天际线），对数深度缓冲有效减少 Z-fighting |
| `stencil` | `true` | 剖切盖面渲染依赖 Stencil Buffer |

**关于对数深度缓冲的取舍**：标准线性深度缓冲在 near/far 比值很大时，近处精度极高而远处精度不足。对数深度缓冲将精度均匀分布在整个深度范围内，代价是微小的性能开销和某些后处理效果的兼容性问题。对于建筑场景（near=0.1, far=100000），这是必要的选择。

阴影贴图类型选择 `VSMShadowMap`（Variance Shadow Map），它能产生天然的软阴影边缘，比 PCF 更平滑，且支持通过 `shadow.radius` 参数控制模糊程度。

## 2. 双相机系统

### 2.1 为什么需要两个相机

建筑可视化有两类截然不同的呈现需求：

**正交相机（OrthographicCamera）**：
- 平面图、立面图、剖面图——建筑制图的标准投影
- 轴测图——不会因距离产生近大远小的透视畸变
- 优势：尺寸可度量，适合分析和技术图纸

**透视相机（PerspectiveCamera）**：
- 人视点效果图——模拟人眼观察建筑的真实感
- 鸟瞰效果图——展示建筑与环境的空间关系
- 两点透视——建筑摄影中保持垂直线平行的经典手法

### 2.2 相机切换的状态同步

切换相机时需要解决的核心问题是 **视点连续性**：用户不应因为切换相机类型而"跳转"到完全不同的视角。

```javascript
// 伪代码：相机切换策略
function switchCamera(targetMode) {
    // 1. 从旧相机复制位置和朝向
    newCamera.position.copy(oldCamera.position)
    newCamera.quaternion.copy(oldCamera.quaternion)

    // 2. 特殊处理：两点透视锁定极角
    if (targetMode === '2pt') {
        controls.minPolarAngle = PI / 2  // 锁定水平
        controls.maxPolarAngle = PI / 2
        newCamera.position.y = controls.target.y  // 对齐目标高度
    }

    // 3. 更新所有引用（控制器、后处理、变换控件）
    controls.object = newCamera
    transformControl.camera = newCamera
    renderPass.camera = newCamera

    // 4. 重新计算投影矩阵
    onResize()
}
```

### 2.3 两点透视的极角锁定技术

两点透视是建筑摄影的经典技法：保持建筑的垂直线在画面中平行（不向消失点汇聚），仅在水平方向产生透视效果。

实现方式是锁定 OrbitControls 的极角（polar angle）为 π/2，使相机始终位于目标点的水平面上。同时将相机 Y 坐标强制对齐到目标点 Y 坐标，确保视线完全水平。

### 2.4 正交相机的视锥体管理

正交相机的视锥体大小直接决定"看到多大范围"。ArchViz-Core 使用模型包围盒尺寸和用户缩放值动态计算：

```
frustumHalfSize = modelSize / viewZoom
left   = -frustumHalfSize × aspect / 2
right  =  frustumHalfSize × aspect / 2
top    =  frustumHalfSize / 2
bottom = -frustumHalfSize / 2
```

这确保了无论模型大小如何，"居中适配"后模型总是合理地填充视口。

## 3. 光照模型

### 3.1 太阳光 + 四方向填充光的设计理由

建筑可视化对光照有特殊要求：既要体现建筑体量感（需要明确的光影方向），又不能有过深的阴影（需要看清所有细节）。

```
              ☀️ Sun Light
              │  (方向可调、投射阴影)
              │
              ▼
    ┌─────────────────────┐
    │                     │
←── Fill ──   模型   ── Fill ──→
    │                     │
    └─────────────────────┘
              │
              ▼
         ── Fill ──
              │
         Top Light ↓
         (从正上方柔和补光)
```

- **太阳光**（DirectionalLight）：唯一投射阴影的光源，方位角 0-360° 可调，模拟一天中太阳位置的变化
- **顶部补光**：消除模型顶面的过暗区域
- **四方向填充光**：±X、±Z 四个方向各一盏，强度较低，确保模型各面都有基础照明

### 3.2 阴影系统

**Shadow Map 分辨率选择**：提供 2048px 和 4096px 两档。4096px 在桌面端提供清晰的阴影边缘，2048px 适合移动端或性能受限场景。

**Bias 调整策略**：Shadow bias 是阴影渲染中最微妙的参数。过大的 bias 导致阴影"飘离"物体（peter-panning），过小的 bias 导致物体表面出现条纹伪影（shadow acne）。

```
shadowBias:       -0.0005  (深度偏移，通常为负值)
shadowNormalBias:  0.02    (沿法线方向偏移，处理曲面伪影)
shadowRadius:      4       (VSM 模糊半径，控制阴影柔和度)
```

### 3.3 阴影相机的自适应包围盒

阴影贴图的精度取决于阴影相机的视锥体覆盖范围——覆盖范围越大，每个像素对应的世界空间面积越大，阴影越模糊。

ArchViz-Core 根据当前模型尺寸动态调整阴影相机的正交视锥体：

```
effectiveSize = max(modelSize, 10)  // 最小保障
frustum = effectiveSize × 0.8       // 紧贴模型
near    = distance × 0.1
far     = distance × 3.0
```

这确保了小模型也能有高精度阴影，大模型不会超出阴影相机的覆盖范围。

## 4. 后期处理链

### 4.1 EffectComposer 的管道模式

Three.js 的 EffectComposer 采用经典的 **管道模式**（Pipeline Pattern）：

```
RenderPass ──▶ EffectPass ──▶ ... ──▶ 屏幕输出
(基础场景)     (视觉效果)

具体管线配置：
┌────────────┐    ┌────────────┐    ┌────────────┐
│ RenderPass │ ──▶│ Sobel Pass │ ──▶│   输出      │  Sketch 模式
│            │    │ (边缘检测) │    │            │
└────────────┘    └────────────┘    └────────────┘

┌────────────┐    ┌────────────┐    ┌────────────┐
│ RenderPass │ ──▶│ Bloom Pass │ ──▶│   输出      │  Bloom 模式
│            │    │ (辉光)     │    │            │
└────────────┘    └────────────┘    └────────────┘

┌────────────┐    ┌────────────┐    ┌────────────┐
│ RenderPass │ ──▶│ DotScreen  │ ──▶│   输出      │  Halftone 模式
│            │    │ (网点)     │    │            │
└────────────┘    └────────────┘    └────────────┘

┌────────────┐    ┌────────────┐    ┌────────────┐
│ RenderPass │ ──▶│ Pixel Pass │ ──▶│   输出      │  PixelArt 模式
│            │    │ (像素化)   │    │            │
└────────────┘    └────────────┘    └────────────┘
```

设计要点：同一时刻只激活一种视觉效果 Pass，它们之间是**互斥**关系。RenderPass 始终作为管线的第一步。

### 4.2 Bloom 效果的 HDR 阈值策略

UnrealBloomPass 的 `threshold` 参数决定了哪些像素参与辉光计算。设定为 0.85 意味着只有亮度超过 85% 的像素才会产生辉光，避免整个画面"发白"。在 Tech 风格中配合高对比度的黑色背景和荧光色边缘，Bloom 效果可以创造赛博朋克般的氛围。

### 4.3 像素化效果的分辨率降采样

自定义 PixelShader 的核心思路是在片段着色器中"量化"UV 坐标：

```
原理：
  pixelatedUV = floor(uv / pixelSize) × pixelSize
  color = texture(scene, pixelatedUV)
```

通过 `pixelSize` 参数控制像素块大小，值越大像素感越强。这比实际降低渲染分辨率更灵活，因为可以在全分辨率下保持 UI 清晰度。

### 4.4 边缘检测的实现思路

Sketch 模式使用 Sobel 算子进行边缘检测。Sobel 算子通过计算图像在水平和垂直方向上的亮度梯度，识别出亮度变化剧烈的区域作为"边缘"。

```
Sobel 核心：
  Gx = [-1 0 +1]    Gy = [-1 -2 -1]
       [-2 0 +2]          [ 0  0  0]
       [-1 0 +1]          [+1 +2 +1]

  edge = sqrt(Gx² + Gy²)
```

Three.js 内置的 SobelOperatorShader 作用于 RenderPass 的输出纹理，将三维场景转换为线稿风格。

## 5. 剖切渲染

### 5.1 ClippingPlane 的基本原理

Three.js 的 ClippingPlane 是一个数学平面 `ax + by + cz + d = 0`。渲染时，GPU 丢弃位于平面"负侧"的所有片段。

ArchViz-Core 支持沿 X / Y / Z 三轴的剖切，并可反转方向：

```
Y 轴剖切示意（俯视图）：

  剖切前:         offset=0(中间):     offset=25%(偏上):
  ┌──────────┐    ┌─────┬────┐        ┌───────┬──┐
  │          │    │可见 │裁剪│        │ 可见  │裁│
  │  模型    │    │     │    │        │       │剪│
  │          │    │     │    │        │       │  │
  └──────────┘    └─────┴────┘        └───────┴──┘
```

### 5.2 Stencil Buffer 三步渲染法

普通的 ClippingPlane 裁剪后，模型内部是"空洞"的——可以看到后面的背景。建筑剖面图通常需要在切割面填充颜色，表示被切割的实体部分。这就需要 **Stencil Buffer 技术**：

```
┌─────────────────────────────────────────────────────────┐
│ Step 1: 渲染背面                                         │
│                                                         │
│  对模型的每个三角面，只渲染背面（BackSide）                 │
│  关闭颜色写入、关闭深度写入                               │
│  Stencil 操作：每个通过的片段，计数器 +1                   │
│                                                         │
│  结果：Stencil Buffer 中记录了"被模型包围的区域"的计数     │
├─────────────────────────────────────────────────────────┤
│ Step 2: 渲染前面                                         │
│                                                         │
│  对模型的每个三角面，只渲染前面（FrontSide）               │
│  关闭颜色写入、关闭深度写入                               │
│  Stencil 操作：每个通过的片段，计数器 -1                   │
│                                                         │
│  结果：只有被剖切穿过的区域，计数器不为零                  │
├─────────────────────────────────────────────────────────┤
│ Step 3: 渲染盖面                                         │
│                                                         │
│  在剖切平面位置放置一个大平面                             │
│  Stencil 测试：只在计数器 ≠ 0 的像素位置渲染              │
│  渲染为用户指定的盖面颜色                                 │
│                                                         │
│  结果：剖切处出现填充色，表示被切割的实体                  │
└─────────────────────────────────────────────────────────┘
```

渲染顺序通过 `renderOrder` 严格控制：
- Stencil 写入网格：`renderOrder = 1.0`
- 盖面平面：`renderOrder = 1.1`
- 模型几何体：`renderOrder = 2.0`
- 叠加层（边缘线等）：`renderOrder = 3.0`

### 5.3 盖面生成的拓扑分析

并非所有网格都适合生成剖切盖面。只有**封闭流形网格**（closed manifold mesh）才能保证 Stencil 计数正确：

- **开放网格**（如单独的平面）：没有"内部"概念，计数器永远不平衡
- **非流形网格**（如 T 形交叉边）：Stencil 计数可能产生伪影

系统通过 **拓扑分析** 预判每个网格是否封闭：

```
1. 焊接顶点（合并位置相近的顶点）
2. 统计每条边被共享的次数：
   - 恰好 2 次 → 流形边
   - 1 次 → 开放边（网格不封闭）
   - >2 次 → 非流形边
3. 如果所有边都是流形边 → 网格封闭，可生成盖面
```

此外还进行了优化：透明材质的薄片物体（如玻璃窗）即使几何封闭也跳过盖面生成，因为它们在视觉上不应该显示实心剖切。

### 5.4 多平面剖切的组合策略

当前版本使用单个剪裁平面。未来扩展到多平面时，需要考虑：

- **交集模式**（AND）：所有平面都裁剪后才显示——用于"切出一个角"
- **并集模式**（OR）：任一平面裁剪即隐藏——用于"切掉多个部分"
- Stencil Buffer 的值域有限（通常 8 位），多平面需要更复杂的 Stencil 策略

## 6. 自定义着色器

### 6.1 高度图着色器的色谱映射

HeightMapShader 将模型顶点的世界空间高度映射为冷暖色谱：

```
颜色映射：

  高度(归一化)   0.0    0.25    0.5    0.75    1.0
  颜色          蓝     →  青   →  绿   →  黄   →  红
                (低)                              (高)

算法：分段线性插值（Piecewise Linear Interpolation）
  t ∈ [0, 0.25) → mix(蓝, 青, t×4)
  t ∈ [0.25, 0.5) → mix(青, 绿, (t-0.25)×4)
  t ∈ [0.5, 0.75) → mix(绿, 黄, (t-0.5)×4)
  t ∈ [0.75, 1.0] → mix(黄, 红, (t-0.75)×4)
```

支持 Y 轴（Three.js 默认上方向）和 Z 轴（Rhino 等 CAD 软件的上方向）两种模式。

### 6.2 深度图着色器

DepthMapShader 将相机空间中的深度值线性映射为灰度：

```
原理：
  depth = -modelViewPosition.z  // 相机空间 Z 轴
  normalizedDepth = (depth - near) / (far - near)
  color = vec3(normalizedDepth)  // 灰度输出
```

近处为黑色，远处为白色。用于辅助理解空间进深关系。

### 6.3 ShaderMaterial 的 Uniform 管理

自定义着色器通过 `uniforms` 对象与 JavaScript 运行时通信：

```javascript
// 伪代码：Uniform 更新模式
shader.uniforms = {
    uMin:  { value: modelBounds.min.y },  // 每次模型加载后更新
    uMax:  { value: modelBounds.max.y },  // 每次模型加载后更新
    uAxis: { value: 0 }                   // 用户切换时更新
}
```

Uniform 更新不会触发着色器重新编译，因此非常高效。但 `onBeforeCompile` 修改着色器源码的方式（如世界网格着色器）会导致材质重新编译，应避免频繁触发。

## 学习要点

1. **对数深度缓冲的应用场景**：当场景的 near/far 比值超过 1:10000 时（建筑场景常见），对数深度缓冲是解决 Z-fighting 的最有效方案。

2. **Stencil Buffer 在建筑可视化中的妙用**：三步渲染法（背面计数 → 前面反计数 → 条件填充）是实现实心剖切面的经典技术，理解这个技巧对图形编程大有裨益。

3. **后期处理的互斥设计**：同一时刻只激活一种视觉效果 Pass 简化了管线管理，避免了效果叠加带来的不可预测结果。

4. **阴影相机的自适应策略**：将阴影相机的视锥体紧贴模型包围盒，是在有限的 Shadow Map 分辨率下获得最佳阴影质量的关键优化。

5. **拓扑分析作为安全网**：在应用高级渲染技术前先验证几何体的拓扑合法性，避免了运行时的视觉伪影。

## 延伸思考

1. **级联阴影贴图（CSM）** 是否适合建筑可视化场景？对于从室内近景到城市远景的大跨度场景，CSM 能提供什么改进？引入 CSM 的复杂度成本是否值得？

2. **如果要支持全局光照（GI）**，在 WebGL 的限制下有哪些可行方案？光照探针（Light Probes）、屏幕空间环境光遮蔽（SSAO）、或者预计算的光照贴图（Lightmaps）——各自的适用场景和性能代价如何？

3. **剖切盖面的"正确"生成方式**：Stencil 法只是一种近似——它无法在盖面上显示切割纹理或材质信息。如果需要在剖面上显示建筑的墙体截面图案（如砖墙截面纹理），应该采用什么技术路线？
