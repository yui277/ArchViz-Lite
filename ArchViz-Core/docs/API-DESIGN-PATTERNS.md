# 后端 API 设计模式

> 本文档只讲设计模式和架构思路，**不包含任何实现代码**，不暴露具体 API 端点。
> 架构概览参见 [整体架构文档](./ARCHITECTURE.md)，AI 集成细节参见 [AI 集成文档](./AI-INTEGRATION.md)。

## 1. API 代理层架构

### 1.1 为什么前端不直接调用第三方 API

三个层面的约束使得后端代理层不可或缺：

**安全层面 — 密钥泄露风险**：
浏览器中的所有 JavaScript 代码对用户完全可见。将 API 密钥嵌入前端代码等同于公开发布密钥。即使通过混淆或环境变量注入，只要密钥出现在网络请求中，任何人都可以通过浏览器开发者工具截获。

**协议层面 — CORS 限制**：
浏览器的同源策略（Same-Origin Policy）禁止前端 JavaScript 向不同域名发起请求，除非目标服务器显式允许。大多数 AI 服务的 API 端点不会为第三方前端配置 CORS 头。

**工程层面 — 请求格式差异**：
不同 AI 服务的认证方式（Bearer Token / HMAC 签名 / API Key Header）、请求格式（JSON 结构差异）和响应格式（字段命名、嵌套层级）各不相同。代理层将这些差异封装在后端，前端只需与一套统一接口交互。

### 1.2 代理层的职责分离

```
前端 POST 请求
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│                    API 代理层                              │
│                                                          │
│  [1] 路由分发  ── 根据 provider/action 参数选择处理逻辑    │
│       │                                                  │
│  [2] 参数校验  ── 检查必填字段、类型、大小限制             │
│       │                                                  │
│  [3] 密钥注入  ── 从环境变量读取密钥，注入请求头            │
│       │                                                  │
│  [4] 请求转发  ── 构造第三方 API 请求，发送并等待          │
│       │                                                  │
│  [5] 响应标准化 ── 提取结果，转换为统一格式                │
│       │                                                  │
│  [6] 错误处理  ── 捕获异常，返回结构化错误信息             │
│                                                          │
└──────────────────────────────────────────────────────────┘
    │
    ▼
前端接收统一格式的响应
```

### 1.3 统一响应格式

所有 API 端点遵循相同的响应结构，无论成功还是失败：

```
成功响应：
{
    "image_url": "https://...",     // 业务数据
    // 或其他业务字段
}

错误响应：
{
    "message": "人类可读的错误描述"   // 始终包含 message 字段
}
HTTP Status: 4xx (客户端错误) / 5xx (服务端错误)
```

这种设计使得前端只需检查 HTTP 状态码即可判断成败，`message` 字段可直接展示给用户。

## 2. HMAC 签名认证

### 2.1 为什么某些云服务需要请求签名

基于 Bearer Token 的认证方式简单但存在安全隐患：如果 Token 被截获，攻击者可以任意伪造请求。请求签名机制提供了更高级别的安全保障：

- **防篡改**：签名覆盖请求方法、路径、查询参数、请求头和请求体。任何修改都会导致签名失效
- **防重放**：签名包含时间戳，服务端拒绝超出时间窗口的请求
- **密钥不上线**：Secret Key 永远不出现在网络请求中——它只在本地参与签名计算

### 2.2 多层密钥推导原理

签名过程不直接使用原始的 Secret Key，而是通过多层 HMAC 哈希逐步派生出最终的签名密钥：

```
密钥推导链（概念示意，非特定服务商）：

Secret Key
    │
    ├── HMAC-SHA256(shortDate)
    │   └── kDate ── 日期绑定（每天轮换）
    │
    ├── HMAC-SHA256(region)
    │   └── kRegion ── 区域绑定
    │
    ├── HMAC-SHA256(service)
    │   └── kService ── 服务绑定
    │
    └── HMAC-SHA256(terminationString)
        └── kSigning ── 最终签名密钥
```

**为什么要多层推导**：

- 每层推导将密钥"绑定"到特定的日期/区域/服务，限制了密钥的作用域
- 即使某一层的中间密钥泄露，它也只能用于特定日期和服务
- 日期层确保了签名密钥每天自动失效

### 2.3 规范化请求的构造规则

签名的输入不是原始 HTTP 请求，而是一个"规范化"后的字符串表示。规范化确保相同逻辑请求总是产生相同的签名：

```
规范化请求 (Canonical Request) 的构成：

  HTTP方法 (大写)
  + '\n'
  + URI路径 (规范化编码)
  + '\n'
  + 查询参数 (按键名字典排序)
  + '\n'
  + 签名头 (按名称字典排序, 小写, 值去空格)
  + '\n'
  + 签名头名称列表 (分号分隔)
  + '\n'
  + 请求体的 SHA256 哈希
```

关键的规范化规则：
- 查询参数按键名的 ASCII 排序
- 头字段名称转小写，值去除首尾空格
- URI 路径中的每个段单独 URL 编码
- 空请求体也要计算 SHA256（得到空字符串的哈希值）

### 2.4 签名算法的通用流程

```
┌─────────────────────────────────────────────────────┐
│ Step 1: 构造规范化请求                                │
│         CanonicalRequest = Method + URI + Query +    │
│                            Headers + PayloadHash     │
├─────────────────────────────────────────────────────┤
│ Step 2: 构造待签名字符串                              │
│         StringToSign = Algorithm + Timestamp +       │
│                        CredentialScope +             │
│                        SHA256(CanonicalRequest)      │
├─────────────────────────────────────────────────────┤
│ Step 3: 推导签名密钥                                  │
│         SigningKey = HMAC链式推导(SK, date, region,   │
│                      service, terminator)            │
├─────────────────────────────────────────────────────┤
│ Step 4: 计算签名                                      │
│         Signature = Hex(HMAC(SigningKey, StringToSign))│
├─────────────────────────────────────────────────────┤
│ Step 5: 构造 Authorization 头                         │
│         Auth = "Algorithm Credential=AK/Scope,       │
│                 SignedHeaders=...,                    │
│                 Signature=..."                        │
└─────────────────────────────────────────────────────┘
```

## 3. 异步任务轮询模式

### 3.1 为什么 AI 渲染是异步的

AI 图像生成涉及大量 GPU 计算，单次推理可能耗时 15-60 秒甚至更长。如果采用同步模式：

- 连接可能超时（大多数 HTTP 代理/负载均衡器的默认超时 < 60s）
- 服务端资源被长时间占用
- 无法实现排队调度（忙时请求无法立即处理）

因此所有 AI 图像服务都采用 **异步任务模式**：创建任务时立即返回任务 ID，客户端后续轮询获取结果。

### 3.2 轮询策略设计

ArchViz-Core 的代理层采用 **固定间隔轮询**，原因及取舍如下：

| 策略 | 描述 | 适用场景 | ArchViz 选择理由 |
|------|------|---------|-----------------|
| 固定间隔 | 每 N 秒查询一次 | 预期耗时稳定 | AI 渲染耗时较可预测（15-45s）|
| 指数退避 | 间隔逐次翻倍 | 耗时不确定 | 对于 AI 渲染场景过于保守 |
| 长轮询 | 服务端挂起连接直到有结果 | 实时性要求高 | 第三方 API 不支持 |
| WebSocket | 双向长连接 | 高频更新 | 架构复杂度不值得 |

具体参数配置：

```
阿里云渠道：
  轮询间隔：2000ms
  最大次数：30 次
  最大等待：~60 秒

FLUX 渠道：
  轮询间隔：1500ms
  最大次数：60 次
  最大等待：~90 秒

火山引擎渠道：
  轮询间隔：可配置（环境变量）
  最大次数：可配置（环境变量）
```

### 3.3 超时处理

当轮询次数用尽仍未获得结果时：

```
轮询循环结束
    │
    ├── 成功状态 + 有结果 URL → 返回结果
    ├── 明确失败状态 → 返回错误 + 失败原因
    └── 循环耗尽 → 返回 HTTP 504 + "超时，请稍后重试"
```

504 Gateway Timeout 的语义准确表达了"代理层等待上游响应超时"的含义。

### 3.4 优雅降级

前端在接收到轮询失败后的处理策略：

```
AI 渲染请求
    │
    ├── 成功 → 显示预览、提供下载
    │
    ├── 超时 (504) → "AI 渲染超时，请稍后重试"
    │                 （保留截图，用户可选择"原截图导出"）
    │
    ├── 服务不可用 (502/503) → "AI 服务暂时不可用"
    │                          （引导用户导出原截图到其他 AI 平台）
    │
    └── 密钥错误 (403) → "请联系开发者"
```

关键设计：**永远提供兜底方案**。即使 AI 渲染完全不可用，用户仍可导出原始截图，通过其他 AI 工具完成风格化处理。

## 4. 多渠道服务抽象

### 4.1 适配器模式的应用

不同 AI 服务的接口差异巨大，但代理层将它们抽象为统一的三步模式：

```
统一接口契约：

输入：{ provider, prompt, image_base64, [options] }
输出：{ image_url } 或 { message }

每个渠道适配器内部实现：

┌───────────────────────────────────┐
│ Step 1: 构造创建任务请求           │
│  - 认证方式不同（Bearer/HMAC/...） │
│  - 参数名不同（prompt/Prompt/...） │
│  - 图片编码方式不同                │
├───────────────────────────────────┤
│ Step 2: 轮询任务状态               │
│  - 查询端点不同                    │
│  - 状态字段名不同                  │
│  - 成功/失败判定逻辑不同           │
├───────────────────────────────────┤
│ Step 3: 提取结果 URL              │
│  - 结果嵌套路径不同                │
│  - URL 字段名不同                  │
└───────────────────────────────────┘
```

### 4.2 渠道选择策略

当前版本由用户在前端手动选择渠道（通过下拉框）。未来可扩展为自动选择：

```
自动渠道选择算法（设计方向）：

1. 可用性检查
   ├── 检查环境变量中是否配置了该渠道的密钥
   └── 未配置 → 从候选列表中排除

2. 成本优先（如果配置了成本权重）
   └── 按单次调用成本排序

3. 质量偏好（如果用户指定了风格偏好）
   └── 不同模型在不同风格上各有优势

4. 负载均衡（如果同时配置了多个可用渠道）
   └── 轮询或随机分配
```

### 4.3 故障转移机制的设计考量

当前版本未实现自动故障转移（一个渠道失败后自动切换到下一个），原因是：

- 不同渠道的图像风格差异较大，自动切换可能不符合用户预期
- 故障转移意味着额外的延迟和资源消耗
- 需要幂等性保证（同一请求在不同渠道上应产生"等价"的结果）

如果未来实现，建议的故障转移策略：

```
请求渠道 A
    │
    ├── 成功 → 返回结果
    └── 失败 → 检查失败类型
        │
        ├── 密钥错误 (403) → 不重试（配置问题）
        ├── 服务过载 (429/503) → 切换到渠道 B
        ├── 超时 (504) → 切换到渠道 B
        └── 内容审核失败 → 不重试（提示词问题）
```

## 5. 安全最佳实践

### 5.1 密钥管理

API 密钥的安全性从高到低排列：

```
安全级别：

 🟢 最佳：系统环境变量
     设置方式：export ARCHVIZ_DEEPSEEK_API_KEY="sk-xxx"
     优势：不存在于任何文件中，进程隔离
     适用：生产环境

 🟡 可接受：服务器变量（Apache/Nginx 配置）
     设置方式：SetEnv ARCHVIZ_DEEPSEEK_API_KEY "sk-xxx"
     优势：不在代码仓库中
     适用：共享主机

 🟠 备用方案：本地配置文件（.gitignore 排除）
     设置方式：secrets.local.php 返回键值数组
     优势：开发环境便利
     风险：可能被误提交到版本控制
     适用：开发环境

 🔴 绝对禁止：硬编码在源代码中
```

ArchViz-Core 的密钥读取函数实现了 **三级环境变量查询**：

```
读取优先级（由高到低）：

1. 系统环境变量 (getenv)
   │
   ▼ 未找到
2. 服务器变量 ($_SERVER / $_ENV)
   │
   ▼ 未找到
3. 本地配置文件 (secrets.local.php)
   │
   ▼ 未找到
4. 返回默认值或报错
```

这种分层查询确保了在不同部署环境下都能找到密钥，同时优先使用最安全的来源。

### 5.2 CORS 策略

```
Origin 白名单 vs 通配符的取舍：

通配符 (Access-Control-Allow-Origin: *)：
  ✅ 简单、适合公共 API
  ❌ 无法携带凭证（cookies）
  ❌ 任何网站都能调用你的 API

白名单 (检查 Origin 后返回特定域名)：
  ✅ 只允许指定域名访问
  ✅ 可以携带凭证
  ❌ 需要维护域名列表
  ❌ 本地开发需要额外配置
```

当前实现在 OPTIONS 预检请求中返回允许的方法和头字段，但未严格限制 Origin——这是为了降低部署复杂度。生产环境建议配置 Origin 白名单。

### 5.3 请求验证

代理层在转发前执行的验证步骤：

```
输入验证清单：

[✓] HTTP 方法检查 ── 只允许 POST
[✓] JSON 格式校验 ── 请求体必须是有效 JSON
[✓] 必填字段检查 ── prompt 非空、image_base64 非空
[✓] Provider 枚举校验 ── 只允许预定义的渠道名
[✓] 环境变量检查 ── 对应渠道的密钥必须存在

未来可扩展：
[ ] 请求体大小限制（防止超大图片 Base64）
[ ] 频率控制（防止单个 IP 过度调用）
[ ] 提示词内容审核（过滤敏感内容）
```

### 5.4 HTTP 客户端安全配置

代理层向第三方服务发起请求时的安全设置：

```
关键配置项：

SSL 验证：
  CURLOPT_SSL_VERIFYPEER = true   ← 验证服务器证书
  CURLOPT_SSL_VERIFYHOST = 2      ← 验证证书主机名

超时控制：
  CURLOPT_CONNECTTIMEOUT = 20     ← 连接超时 20 秒
  CURLOPT_TIMEOUT = 120           ← 总超时 120 秒

重定向：
  CURLOPT_FOLLOWLOCATION = true   ← 跟随 HTTP 重定向
```

**绝不关闭 SSL 验证**——即使在开发环境中。关闭 SSL 验证等同于接受中间人攻击。

## 学习要点

1. **API 代理层是前后端分离架构中 AI 集成的必要组件**。它不是可选的"锦上添花"，而是安全性、CORS 合规和接口标准化的根基。

2. **HMAC 签名认证的多层密钥推导**：通过将密钥绑定到日期/区域/服务，实现了细粒度的访问控制和自动的密钥轮换。理解这个模式有助于对接任何需要请求签名的云服务。

3. **异步任务的轮询模式选择**：在 AI 服务场景中，固定间隔轮询是简单性和效率的最佳平衡。指数退避适合不确定延迟的场景，长轮询/WebSocket 适合实时性要求极高的场景。

4. **三级环境变量查询**：系统环境变量 → 服务器变量 → 本地配置文件的分层查询，在安全性和开发便利性之间找到了实用的平衡点。

5. **优雅降级的设计哲学**：AI 功能的不可用不应阻塞用户的核心工作流。始终提供非 AI 的兜底方案（如原截图导出），确保系统在最坏情况下仍然可用。

## 延伸思考

1. **如果要支持 WebSocket 推送模式**替代轮询，代理层的架构需要做哪些改变？是维护一个长连接池还是引入消息队列（如 Redis Pub/Sub）？对于 PHP 这种传统的请求-响应模型，WebSocket 支持的技术选型有哪些（如 Swoole、Ratchet、或者干脆换成 Node.js）？

2. **密钥轮换的自动化**：当前的密钥是静态配置的。在高安全要求的场景下，如何实现自动的密钥轮换？是否应该引入 Vault 之类的密钥管理服务？密钥轮换期间如何保证零停机？

3. **多渠道的成本优化**：如果同时接入了多个 AI 渲染服务，是否可以根据用户的提示词内容（如"写实" vs "艺术风格"）自动选择最适合的渠道？这种"智能路由"需要什么样的评估指标和 A/B 测试框架？
