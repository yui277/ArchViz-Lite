# 后端 API 设计模式

> 本文档只讲设计模式和架构思路，**不包含任何实现代码**，不暴露具体 API 端点。
> 架构概览参见 [整体架构文档](./ARCHITECTURE.md)，AI 集成细节参见 [AI 集成文档](./AI-INTEGRATION.md)。

## 1. API 代理层架构

### 1.1 代理层职责

```
前端 POST 请求
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│                    API 代理层                              │
│                                                          │
│  [1] 路由分发  ── 根据 provider/action 参数选择处理逻辑    │
│       │                                                  │
│  [2] 参数校验  ── 检查必填字段、类型、大小限制             │
│       │                                                  │
│  [3] 密钥注入  ── 从环境变量读取密钥，注入请求头            │
│       │                                                  │
│  [4] 请求转发  ── 构造第三方 API 请求，发送并等待          │
│       │                                                  │
│  [5] 响应标准化 ── 提取结果，转换为统一格式                │
│       │                                                  │
│  [6] 错误处理  ── 捕获异常，返回结构化错误信息             │
│                                                          │
└──────────────────────────────────────────────────────────┘
    │
    ▼
前端接收统一格式的响应
```

### 1.2 统一响应格式

所有 API 端点遵循相同的响应结构，无论成功还是失败：

```
成功响应：
{
    "image_url": "https://...",     // 业务数据
    // 或其他业务字段
}

错误响应：
{
    "message": "人类可读的错误描述"   // 始终包含 message 字段
}
HTTP Status: 4xx (客户端错误) / 5xx (服务端错误)
```

前端只需检查 HTTP 状态码判断成败，`message` 字段可直接展示给用户。

## 2. HMAC 签名认证

### 2.1 多层密钥推导

签名过程不直接使用原始的 Secret Key，而是通过多层 HMAC 哈希逐步派生出最终的签名密钥：

```
密钥推导链（概念示意，非特定服务商）：

Secret Key
    │
    ├── HMAC-SHA256(shortDate)
    │   └── kDate ── 日期绑定（每天轮换）
    │
    ├── HMAC-SHA256(region)
    │   └── kRegion ── 区域绑定
    │
    ├── HMAC-SHA256(service)
    │   └── kService ── 服务绑定
    │
    └── HMAC-SHA256(terminationString)
        └── kSigning ── 最终签名密钥
```

每层推导将密钥绑定到特定日期/区域/服务，限制作用域，日期层确保签名密钥每天自动失效。

### 2.2 规范化请求

```
规范化请求 (Canonical Request) 的构成：

  HTTP方法 (大写)
  + '\n'
  + URI路径 (规范化编码)
  + '\n'
  + 查询参数 (按键名字典排序)
  + '\n'
  + 签名头 (按名称字典排序, 小写, 值去空格)
  + '\n'
  + 签名头名称列表 (分号分隔)
  + '\n'
  + 请求体的 SHA256 哈希
```

关键的规范化规则：
- 查询参数按键名的 ASCII 排序
- 头字段名称转小写，值去除首尾空格
- URI 路径中的每个段单独 URL 编码
- 空请求体也要计算 SHA256（得到空字符串的哈希值）

### 2.3 签名流程

```
┌─────────────────────────────────────────────────────┐
│ Step 1: 构造规范化请求                                │
│         CanonicalRequest = Method + URI + Query +    │
│                            Headers + PayloadHash     │
├─────────────────────────────────────────────────────┤
│ Step 2: 构造待签名字符串                              │
│         StringToSign = Algorithm + Timestamp +       │
│                        CredentialScope +             │
│                        SHA256(CanonicalRequest)      │
├─────────────────────────────────────────────────────┤
│ Step 3: 推导签名密钥                                  │
│         SigningKey = HMAC链式推导(SK, date, region,   │
│                      service, terminator)            │
├─────────────────────────────────────────────────────┤
│ Step 4: 计算签名                                      │
│         Signature = Hex(HMAC(SigningKey, StringToSign))│
├─────────────────────────────────────────────────────┤
│ Step 5: 构造 Authorization 头                         │
│         Auth = "Algorithm Credential=AK/Scope,       │
│                 SignedHeaders=...,                    │
│                 Signature=..."                        │
└─────────────────────────────────────────────────────┘
```

## 3. 异步任务轮询模式

### 3.1 轮询策略设计

| 策略 | 描述 | 适用场景 | ArchViz 选择理由 |
|------|------|---------|-----------------|
| 固定间隔 | 每 N 秒查询一次 | 预期耗时稳定 | AI 渲染耗时较可预测（15-45s）|
| 指数退避 | 间隔逐次翻倍 | 耗时不确定 | 对于 AI 渲染场景过于保守 |
| 长轮询 | 服务端挂起连接直到有结果 | 实时性要求高 | 第三方 API 不支持 |
| WebSocket | 双向长连接 | 高频更新 | 架构复杂度不值得 |

具体参数配置：

```
阿里云渠道：
  轮询间隔：2000ms
  最大次数：30 次
  最大等待：~60 秒

FLUX 渠道：
  轮询间隔：1500ms
  最大次数：60 次
  最大等待：~90 秒

火山引擎渠道：
  轮询间隔：可配置（环境变量）
  最大次数：可配置（环境变量）
```

### 3.2 超时处理

当轮询次数用尽仍未获得结果时：

```
轮询循环结束
    │
    ├── 成功状态 + 有结果 URL → 返回结果
    ├── 明确失败状态 → 返回错误 + 失败原因
    └── 循环耗尽 → 返回 HTTP 504 + "超时，请稍后重试"
```

504 Gateway Timeout 的语义准确表达了"代理层等待上游响应超时"的含义。

### 3.3 优雅降级

```
AI 渲染请求
    │
    ├── 成功 → 显示预览、提供下载
    │
    ├── 超时 (504) → "AI 渲染超时，请稍后重试"
    │                 （保留截图，用户可选择"原截图导出"）
    │
    ├── 服务不可用 (502/503) → "AI 服务暂时不可用"
    │                          （引导用户导出原截图到其他 AI 平台）
    │
    └── 密钥错误 (403) → "请联系开发者"
```

核心设计：AI 功能不可用不应阻塞用户核心工作流，始终提供原始截图导出作为兆底。

## 4. 多渠道服务抽象

### 4.1 适配器模式的应用

不同 AI 服务的接口差异巨大，但代理层将它们抽象为统一的三步模式：

```
统一接口契约：

输入：{ provider, prompt, image_base64, [options] }
输出：{ image_url } 或 { message }

每个渠道适配器内部实现：

┌───────────────────────────────────┐
│ Step 1: 构造创建任务请求           │
│  - 认证方式不同（Bearer/HMAC/...） │
│  - 参数名不同（prompt/Prompt/...） │
│  - 图片编码方式不同                │
├───────────────────────────────────┤
│ Step 2: 轮询任务状态               │
│  - 查询端点不同                    │
│  - 状态字段名不同                  │
│  - 成功/失败判定逻辑不同           │
├───────────────────────────────────┤
│ Step 3: 提取结果 URL              │
│  - 结果嵌套路径不同                │
│  - URL 字段名不同                  │
└───────────────────────────────────┘
```

### 4.2 渠道选择策略

当前由用户手动选择渠道。自动选择的设计方向：可用性检查（密钥是否配置）→ 成本优先 → 质量偏好 → 负载均衡。

### 4.3 故障转移机制

当前未实现自动故障转移，原因：不同渠道的图像风格差异大，自动切换可能不符合用户预期；额外延迟和资源消耗；缺乏幂等性保证。

建议的故障转移策略：密钥错误 (403) 和内容审核失败不重试；服务过载 (429/503) 和超时 (504) 切换渠道。

## 5. 安全最佳实践

### 5.1 密钥管理

API 密钥安全级别：

- **最佳**：系统环境变量（不存在于任何文件，进程隔离）
- **可接受**：服务器变量（Apache/Nginx 配置，不在代码仓库中）
- **开发用**：本地配置文件（.gitignore 排除）
- **绝对禁止**：硬编码在源码中

密钥读取实现三级查询：系统环境变量 (getenv) → 服务器变量 ($_SERVER/$_ENV) → 本地配置文件 (secrets.local.php)，优先使用最安全的来源。

### 5.2 CORS 策略

当前在 OPTIONS 预检请求中未严格限制 Origin（降低部署复杂度）。生产环境建议配置 Origin 白名单，支持凭证携带并限制访问来源。

### 5.3 请求验证

代理层在转发前执行的验证步骤：

```
输入验证清单：

[✓] HTTP 方法检查 ── 只允许 POST
[✓] JSON 格式校验 ── 请求体必须是有效 JSON
[✓] 必填字段检查 ── prompt 非空、image_base64 非空
[✓] Provider 枚举校验 ── 只允许预定义的渠道名
[✓] 环境变量检查 ── 对应渠道的密钥必须存在

未来可扩展：
[ ] 请求体大小限制（防止超大图片 Base64）
[ ] 频率控制（防止单个 IP 过度调用）
[ ] 提示词内容审核（过滤敏感内容）
```

### 5.4 HTTP 客户端安全配置

代理层向第三方服务发起请求时的安全配置：SLL 验证开启（VERIFYPEER=true, VERIFYHOST=2）、连接超时 20s / 总超时 120s、跟随 HTTP 重定向。SSL 验证在任何环境下都不应关闭。

## 技术要点

1. **API 代理层**：安全性、CORS 合规和接口标准化的必要组件，承担密钥保护、请求转换和错误标准化职责。

2. **HMAC 多层密钥推导**：通过将密钥绑定到日期/区域/服务，实现细粒度访问控制和自动密钥轮换。

3. **轮询策略选择**：AI 渲染耗时较可预测，固定间隔轮询是简单性和效率的最佳平衡。

4. **三级环境变量查询**：系统环境变量 → 服务器变量 → 本地配置文件，在安全性和开发便利性间取得平衡。

5. **优雅降级**：AI 功能不可用不应阻塞核心工作流，始终提供非 AI 的兆底方案（原始截图导出）。
