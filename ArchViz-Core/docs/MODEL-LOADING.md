# 模型加载策略文档

> 本文档详解 ArchViz-Core 的多格式 3D 资产加载管线，包括格式对比、坐标系转换、单位系统、性能优化和 Rhino 格式深度解析。
> 架构概览参见 [整体架构文档](./ARCHITECTURE.md)，渲染相关细节参见 [渲染管线文档](./RENDERING-PIPELINE.md)。

## 1. 支持格式对比

### 1.1 格式特性矩阵

| 特性 | .3dm (Rhino) | .gltf/.glb (glTF 2.0) | .obj (Wavefront) |
|------|-------------|----------------------|-----------------|
| **原始几何** | NURBS 曲面 | 三角面片 | 三角/四边面片 |
| **材质支持** | Rhino 材质 | PBR 金属度/粗糙度 | 无（需 .mtl 文件） |
| **纹理嵌入** | 否 | .glb 内嵌 | 否 |
| **压缩** | 否 | Draco 几何压缩 | 否 |
| **坐标系** | Z-up（右手系） | Y-up（右手系） | Y-up（通常） |
| **解析方式** | rhino3dm.wasm | 内置/Draco WASM | 纯文本解析 |
| **文件体积** | 中等 | 小（压缩后极小） | 大（纯文本） |
| **行业应用** | 建筑/工业设计 | Web/游戏/通用 | 通用交换格式 |

### 1.2 格式选择决策树

```
你的模型来自哪里？
    │
    ├── Rhino / Grasshopper
    │   └── 使用 .3dm ── NURBS 精度最高，保留图层信息
    │
    ├── SketchUp / Blender / 3ds Max
    │   └── 导出为 .glb ── Draco 压缩体积最小，PBR 材质完整
    │
    ├── 通用交换（任何软件）
    │   └── 使用 .obj ── 兼容性最广，但丢失材质信息
    │
    └── 已有 Web 优化资产
        └── 使用 .gltf ── glTF 2.0 是 Web 3D 的"JPEG"
```

## 2. 坐标系转换

### 2.1 Z-up vs Y-up 的行业差异

这是 3D 行业中最常见的混淆来源之一：

```
Z-up（建筑 CAD 惯例）          Y-up（Three.js / WebGL 惯例）

        Z ↑                            Y ↑
        │                              │
        │                              │
        │                              │
        └──── Y                        └──── X
       /                              /
      X                              Z

  Rhino, AutoCAD,               Three.js, Unity,
  Grasshopper, GIS              Unreal, glTF
```

**历史原因**：建筑和测绘领域习惯用 X-Y 表示平面位置、Z 表示高度；而计算机图形学（OpenGL/WebGL）源自屏幕坐标系，X 向右、Y 向上、Z 朝向观察者。

### 2.2 自动检测策略

ArchViz-Core 采用 **格式元数据优先 + 启发式辅助** 的检测策略：

```
检测流程：

1. 格式元数据判断（最可靠）
   ├── .3dm 文件 → 必定是 Z-up（Rhino 规范）
   └── .gltf/.glb → 必定是 Y-up（glTF 2.0 规范）

2. OBJ 格式的启发式判断（备用方案）
   ├── 计算模型包围盒
   ├── 分析 Y 轴和 Z 轴的范围比
   │   ├── 如果 Z 轴范围 >> X/Y 轴范围（呈"塔"形） → 可能是 Z-up
   │   └── 如果 Y 轴范围 >> X/Z 轴范围（呈"塔"形） → 可能是 Y-up
   └── 不确定时提供用户确认机制
```

### 2.3 变换矩阵的应用时机

坐标系转换在 **加载时** 执行（而非运行时），通过绕 X 轴旋转 -90° 实现：

```javascript
// 伪代码：Z-up → Y-up 转换
if (format.zUp) {
    modelRoot.rotation.x = -Math.PI / 2  // 绕X轴旋转-90度
    modelRoot.updateMatrixWorld()
}
```

在加载时处理的好处：
- 后续所有操作（包围盒计算、剖切、阴影等）都在统一的 Y-up 空间中进行
- 避免运行时的矩阵乘法开销
- 用户可通过 "旋转修正" 开关手动切换，应对自动检测失败的情况

## 3. 单位系统

### 3.1 建筑模型的常见单位

| 单位 | 换算到米 | 常见来源 |
|------|---------|---------|
| 米 (m) | 1.0 | Rhino（取决于模板）、SketchUp |
| 毫米 (mm) | 0.001 | AutoCAD、Revit、工业设计 |
| 厘米 (cm) | 0.01 | 部分 Blender 导出 |
| 英寸 (in) | 0.0254 | 美国建筑实践 |
| 英尺 (ft) | 0.3048 | 美国建筑实践 |

### 3.2 自动缩放校准策略

当前版本提供 **用户确认机制**：加载文件时弹出对话框让用户选择单位（米/毫米）。

自动检测的思路（未来方向）：

```
自动单位推断算法（启发式）：

1. 计算模型包围盒的最大维度 maxDim
2. 推断原始单位：
   ├── maxDim ∈ [0.1, 500]    → 可能是米（建筑尺度合理）
   ├── maxDim ∈ [100, 500000] → 可能是毫米（除以1000后合理）
   ├── maxDim ∈ [1, 5000]     → 可能是厘米（除以100后合理）
   └── 不确定时弹出用户确认
3. 辅助判断：
   ├── 如果存在已知尺寸的参考物（如门高约2.1m）
   └── 如果文件元数据中包含单位信息（部分格式支持）
```

### 3.3 毫米到米的转换实现

当用户选择"毫米"时，对模型根节点应用均匀缩放：

```javascript
// 伪代码
if (unit === 'mm') {
    root.scale.set(0.001, 0.001, 0.001)
}
```

缩放在 `processModel()` 的最早阶段执行，确保后续的包围盒计算、居中、光照适配等操作都基于正确的米制尺寸。

## 4. 性能优化

### 4.1 高多边形检测

```
顶点数量分级：

  < 200万   → 正常流程，无提示
  200万-500万 → 显示警告弹窗，提示可能卡顿
  > 500万   → 建议进行减面优化后再加载
```

**为什么选择 200 万作为预警阈值**：

- WebGL 1.0 的索引缓冲区限制为 65535（通过分割可绕过）
- 主流移动设备的 GPU 在 100-200 万三角面时开始出现明显帧率下降
- 建筑模型中 200 万顶点通常对应一个中等复杂度的方案模型
- 超过这个阈值，阴影计算和后期处理的开销会显著增加

### 4.2 几何体优化

模型加载后执行以下优化步骤：

```
遍历所有子节点：
    │
    ├── 检查法线 ── 缺失则调用 computeVertexNormals()
    │               （PBR 光照依赖法线数据）
    │
    ├── 清理顶点色 ── deleteAttribute('color')
    │                 （避免与材质颜色冲突）
    │
    ├── 启用阴影 ── castShadow = true, receiveShadow = true
    │
    ├── 备份材质 ── userData.originalMat = material.clone()
    │               （支持风格预设后恢复原始材质）
    │
    ├── 禁用视锥裁剪 ── frustumCulled = false
    │                    （建筑模型通常始终在视野中）
    │
    └── 记录初始变换 ── userData.initPos / initRot / initScale
                        （支持"重置位置"功能）
```

### 4.3 LOD（细节层次）策略的考量

当前版本未实现 LOD，但设计时预留了扩展空间。对于建筑可视化的 LOD，需要考虑以下特殊性：

- **建筑几何的规则性**：建筑模型以直线和平面为主，简化时不应引入曲面近似误差
- **边缘的视觉重要性**：建筑的轮廓线是识别建筑的关键，LOD 切换不应改变轮廓
- **基于距离 vs 基于屏幕面积**：对于正交相机，距离无意义（无透视缩小），应使用屏幕面积作为 LOD 切换依据

### 4.4 WebWorker 异步加载的架构考虑

rhino3dm.wasm 的 NURBS 镶嵌和 Draco 的几何解压缩都是 CPU 密集型操作。Three.js 的加载器已内置了一定程度的异步处理（通过回调或 Promise），但主线程的 JSON 解析和场景图构建仍可能阻塞 UI。

更进一步的优化方向是将整个 `processModel()` 后处理管线移入 WebWorker，但挑战在于 Three.js 对象不可直接在 Worker 间传递——需要通过 Transferable 对象（ArrayBuffer）中转。

## 5. Rhino 格式深度解析

### 5.1 rhino3dm.wasm 的加载机制

Rhino3dmLoader 依赖 `rhino3dm.wasm`，这是 openNURBS 库的 WebAssembly 编译版本。加载流程：

```
Rhino3dmLoader.setLibraryPath(cdnUrl)
    │
    ▼
首次调用 load() 时：
    ├── 下载 rhino3dm.wasm (~2.5MB)
    ├── 实例化 WASM 模块
    └── 缓存到内存（后续加载不重复下载）
    │
    ▼
解析 .3dm 文件：
    ├── 读取文件头：版本号、单位、坐标系
    ├── 提取对象表：几何体、图层、材质、用户数据
    └── 逐对象转换为 Three.js 几何体
```

CDN 路径使用 jsDelivr 托管的 rhino3dm@8.4.0 版本，确保全球加速和版本锁定。

### 5.2 NURBS 到 Mesh 的镶嵌过程

Rhino 的原生几何是 NURBS 曲面（非均匀有理 B 样条），而 WebGL 只能渲染三角面片。镶嵌（Tessellation）过程在 WASM 中完成：

```
NURBS 曲面
    │
    ▼
参数域采样 ── 在 u-v 参数空间中生成采样网格
    │
    ▼
求值 ── 对每个 (u,v) 点计算 3D 坐标、法线、切线
    │
    ▼
三角化 ── 将采样网格转换为三角面片
    │
    ▼
法线平滑 ── 基于曲面连续性计算顶点法线
    │
    ▼
Three.js BufferGeometry
```

镶嵌精度由 rhino3dm 内部的公差参数控制。对于建筑模型，默认精度通常足够——建筑几何以平面为主，曲面相对少见。

### 5.3 图层、材质与用户数据的提取

.3dm 文件不仅包含几何体，还携带丰富的元数据：

- **图层信息**：建筑模型的图层组织（如"墙体"、"楼板"、"幕墙"）
- **材质属性**：Rhino 的渲染材质（漫反射色、透明度等）
- **用户数据**：Grasshopper 参数化设计附加的自定义属性

当前版本在加载时提取了材质信息（存入 `userData.originalMat`），但图层信息和用户数据尚未充分利用。这些元数据为未来的按图层过滤、属性查询等功能提供了基础。

### 5.4 线段几何的特殊处理

Rhino 模型中常包含曲线/线段（如辅助线、标注线）。这些被转换为 `THREE.LineSegments`，需要特殊的材质处理：

```
遍历加载结果中的线段对象：
    │
    ├── 检查线段颜色
    │   ├── 如果为纯黑 (0,0,0) → 替换为深灰 (0x333333)
    │   │   （纯黑线段在黑色背景下不可见）
    │   └── 否则保留原始颜色
    │
    └── 设置 LineBasicMaterial
        （线段不参与阴影和后期处理）
```

## 6. 加载重试与代理回退

网络环境的不确定性要求加载管线具备容错能力：

```
load(url)
    │
    ├── 直连尝试
    │   ├── 成功 → 进入 processModel()
    │   └── 失败 → 启动代理回退
    │
    ├── 代理 1 (corsproxy.io)
    │   ├── 成功 → 进入 processModel()
    │   └── 失败 → 尝试下一个代理
    │
    ├── 代理 2 (codetabs.com)
    │   ├── 成功 → 进入 processModel()
    │   └── 失败 → 尝试下一个代理
    │
    └── 代理 3 (allorigins.win)
        ├── 成功 → 进入 processModel()
        └── 失败 → 报告错误，建议用户检查网络
```

通过代理 URL 加载时，需要从代理 URL 中提取原始文件扩展名，以正确选择加载器。这是一个容易被忽视的边界情况。

## 学习要点

1. **坐标系转换的重要性**：Z-up 和 Y-up 的差异看似简单，但如果不在加载时统一处理，后续的剖切方向、光照角度、阴影投射都会出错。格式元数据驱动的自动检测是最可靠的方案。

2. **材质备份模式**：在加载时 `clone()` 并备份原始材质，使得风格预设切换后能够无损恢复——这是一个典型的 Memento（备忘录）模式应用。

3. **渐进式容错设计**：直连 → 代理 1 → 代理 2 → 代理 3 的回退链，确保在各种网络环境下（企业内网、移动网络、海外访问）都有最大的加载成功率。

4. **WASM 在 Web 3D 中的角色**：rhino3dm.wasm 展示了 WebAssembly 如何将原本只能在桌面端运行的 CAD 格式解析能力带入浏览器——这是 Web 3D 生态日趋成熟的标志。

5. **性能阈值的选择依据**：200 万顶点的预警阈值不是拍脑袋决定的，而是基于目标设备 GPU 能力、WebGL 限制和典型建筑模型复杂度的综合考量。

## 延伸思考

1. **自动 LOD 生成**在建筑可视化中面临独特挑战：网格简化算法（如 QEM）可能破坏建筑的直线和直角特征。是否存在"建筑感知"的网格简化算法，能在减面的同时保留建筑的几何特征？

2. **增量加载**：对于超大模型（如整个城市的 BIM 模型），是否可以设计基于视距的增量加载策略——先加载近处的高精度模型，远处先用简化代理几何体占位？

3. **格式转换的性能优化**：rhino3dm 的 NURBS 镶嵌是加载 .3dm 文件的主要瓶颈。如果在服务器端预先将 .3dm 转换为 .glb 并缓存结果，对于重复访问的模型能显著提升加载速度。这种"编译时优化"策略在实际项目中如何实施？
