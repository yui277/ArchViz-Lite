# ArchViz-Core 整体架构设计

> 本文档面向希望理解 ArchViz-Core 内部运作机制的开发者和建筑可视化技术爱好者。

## 1. 项目概述

ArchViz-Core 是一个基于 **Three.js** 的轻量级建筑可视化引擎，运行于现代浏览器中，旨在解决以下核心问题：

- **跨平台建筑模型预览**：无需安装专业软件（如 Rhino、SketchUp），在任何设备上快速查看 .3dm / .glb / .obj 格式的建筑模型
- **多风格快速表现**：一键切换素模、蓝图、X光、手绘等十余种建筑表现风格
- **交互式分析**：剖切、测量、尺度参照等建筑分析功能
- **AI 驱动的动画与渲染**：通过自然语言描述生成动画脚本，并接入多个 AI 图像生成服务实现风格化渲染

**目标用户**：建筑设计师、城市规划师、设计院校学生，以及对 WebGL 建筑可视化技术感兴趣的前端工程师。

### 2.2 分层设计

系统采用 **五层架构**，每层职责清晰且单向依赖：

| 层级 | 名称 | 核心职责 | 关键文件 |
|------|------|----------|----------|
| L1 | 表现层 | HTML 结构、CSS 样式、DOM 操作抽象 | `archvizlite.html`, `main.css` |
| L2 | 交互层 | 指针事件归一化、工具模式状态机、快捷键 | `InteractionManager.js` |
| L3 | 引擎层 | 场景图、双相机、渲染器、渲染循环 | `ArchVizEngine.js` |
| L4 | 模块层 | 各功能领域的独立实现 | `modules/*.js` |
| L5 | 服务层 | API 代理、密钥管理、请求转发 | `api/*.php` |

## 3. 核心设计原则

### 3.1 配置驱动

所有运行时行为均由 `CONFIG` 对象参数化。这意味着：

- **场景默认值**（背景色、光照强度、阴影分辨率）不散落在代码各处
- **API 端点和密钥**集中管理，通过环境变量注入
- **功能开关**（如 showcaseMode）控制启动行为
- **阈值参数**（如高多边形警告阈值 2M 顶点）可配置

```javascript
// 伪代码：配置结构示意
CONFIG = {
    APP: { showcaseMode, version },
    DEFAULTS: { background, model, lighting, camera, ... },
    API_ENDPOINTS: { DEEPSEEK, ALIYUN, FLUX, VOLCANO },
    API_KEYS: { /* 从环境变量读取 */ },
    AI_ANIMATION: { model, temperature, maxRetries, ... },
    SMART_EXPORT: { channels, promptPresets, batchConfigTypes }
}
```

### 3.2 策略模式（Strategy Pattern）

工具模式切换是策略模式的典型应用：

```
InteractionManager.setToolMode(mode)
    │
    ├── VIEW    → OrbitControls 激活，自由导航
    ├── RULER   → Raycaster 拾取边缘，计算距离
    ├── MOVE    → TransformControls 附着到选中对象
    ├── HIDE    → 点击对象切换可见性
    └── SECTION → 拖拽调整剖切平面位置
```

每次模式切换遵循 **清理旧状态 → 更新状态标记 → 激活新行为 → 通知外部** 的四步流程。

### 3.3 观察者模式（Observer Pattern）

`InteractionManager.onStateChange(key, value)` 提供了状态变更的通知接口。外部 UI 层通过覆写此方法实现响应式更新，而无需交互层了解 UI 的具体实现。

### 3.4 关注点分离

- **渲染**（ArchVizEngine）不关心材质从哪来——由 ModelLoader 负责
- **交互**（InteractionManager）不关心渲染细节——只操作抽象的相机和控制器
- **UI** 不关心 AI 如何调用——只触发 `generateAnimationScript()` 并等待结果
- **API 代理** 不关心前端逻辑——只负责认证、转发和错误标准化

## 4. 数据流

### 4.1 用户操作流

```
用户操作（点击/拖拽/键盘）
    │
    ▼
InteractionManager（事件归一化、模式分发）
    │
    ├── 视图操作 ──▶ OrbitControls ──▶ 相机矩阵更新 ──▶ 渲染循环自动刷新
    ├── 工具操作 ──▶ Raycaster 拾取 ──▶ 状态变更 ──▶ UI 同步
    └── 参数调整 ──▶ State 对象更新 ──▶ 相关模块 .update() ──▶ 场景重绘
```

### 4.2 AI 请求流

```
用户输入自然语言描述
    │
    ▼
AIAnimationPlanner.generatePlan()
    │
    ├── 构造 System Prompt（角色 + 能力清单 + 格式约束）
    ├── POST → API 代理层 → DeepSeek LLM
    ├── 解析 JSON 响应 → 校验 → 自动修复
    │
    ▼
AIAnimationExecutor.buildTimeline()
    │
    ├── 分镜 → 底层动作转译
    ├── 逐帧插值执行
    └── 同步录制器捕获画面
```

## 5. 状态管理

系统维护三类运行时状态：

### 5.1 引擎状态

由 `ArchVizEngine` 实例持有，包括场景图（`scene`）、活动相机（`activeCamera`）、渲染器（`renderer`）、剪裁平面（`clipPlanes`）、场景组层级（`groups`）等。这些是 Three.js 级别的对象引用。

### 5.2 交互状态

由 `InteractionManager` 管理，包括当前工具模式（`activeTool`）、选中对象列表（`selection`）、隐藏对象列表（`hiddenObjects`）、视口快照（`viewport`）等。

### 5.3 配置状态

由 `CONFIG` 和运行时 `State` 对象共同维持。`State` 是一个扁平的键值对象，存储所有可调参数（材质类型、光照强度、剖切偏移等）。GUI 控件直接绑定到 `State` 的属性上，修改即时生效。

```
CONFIG（静态配置，启动时读取）
    │
    ▼
State（运行时状态，GUI 双向绑定）
    │
    ├── 材质变更 ──▶ ModelManager.updateMaterials()
    ├── 光照变更 ──▶ Lighting.update()
    ├── 剖切变更 ──▶ ModelManager.updateSection()
    └── 后期效果 ──▶ PostProcessing.updateMode()
```

## 6. 模块职责表

| 模块 | 单一职责 | 主要输入 | 主要输出 |
|------|---------|---------|---------|
| `config.js` | 集中式配置定义与校验 | 环境变量、默认值 | `CONFIG` 对象 |
| `ArchVizEngine` | WebGL 渲染生命周期管理 | CONFIG、DOM 容器 | 场景图、渲染帧 |
| `InteractionManager` | 跨设备输入处理与工具状态机 | PointerEvent、KeyboardEvent | 状态变更回调 |
| `ModelLoader` | 多格式 3D 资产加载与预处理 | 文件 URL/File、单位参数 | 处理后的 Object3D |
| `LightingSystem` | 多光源照明与阴影配置 | 光照参数、模型包围盒 | 场景中的 Light 对象 |
| `SectionCut` | Stencil Buffer 剖切渲染 | 剖切轴/偏移/反向 | 剪裁平面、盖面几何体 |
| `PostProcessing` | EffectComposer 后期处理管线 | 渲染模式（Sketch/Bloom/...） | 屏幕后期效果 |
| `AIAnimation` | 双阶段 AI 动画脚本生成与执行 | 自然语言描述 | 可执行的动画时间线 |
| `SmartExport` | 多渠道 AI 渲染与批量出图 | 视口截图 + 提示词 | AI 渲染结果图片 |
| `CustomShaders` | 分析用自定义 GLSL 着色器 | 模型几何体、Uniforms | 高度图/深度图/像素化效果 |

## 学习要点

1. **分层架构的价值**：表现层、交互层、引擎层、模块层、服务层的分离使得任何一层的重构不会波及其他层。例如，将 UI 从 lil-gui 换成 React 只需要替换表现层和交互层的绑定代码。

2. **配置驱动设计**：将所有魔法数字和行为参数提取到统一的 CONFIG 对象中，不仅提高了代码可读性，还使得部署到不同环境（开发/测试/生产）成为一个配置切换问题而非代码修改问题。

3. **策略模式在交互系统中的应用**：通过工具模式状态机将不同交互行为封装为独立策略，切换时只需清理旧状态并激活新策略，避免了大量的条件分支。

4. **模块化设计的边界划分**：每个模块拥有明确的「单一职责」和「输入/输出契约」，模块间通过引擎层的 `_modules` 注册表互相引用，而非直接耦合。

5. **前后端分离中 API 代理层的必要性**：浏览器端无法安全持有 API 密钥，CORS 限制也阻止直接调用第三方服务。代理层同时承担了密钥保护、请求格式转换和错误标准化的职责。

## 延伸思考

1. **如果要将此引擎集成到 React/Vue 项目中**，你会如何重构表现层和交互层？状态管理是否应该迁移到框架的响应式系统（如 Redux/Pinia）中？

2. **当前的模块注册机制是运行时手动组装的**。如果引入依赖注入（DI）容器或模块联邦（Module Federation），对架构的可测试性和可扩展性会产生什么影响？

3. **配置驱动设计的极端情况**：当配置项数量增长到数百个时，如何设计配置的分层覆盖（默认值 → 用户偏好 → 项目级配置 → 运行时调整）以避免配置爆炸？
